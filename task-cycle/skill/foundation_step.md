# The foundation step

Read by the agent that writes the entries the task carries — the one author with its code, the
agent of a plan's *Foundation entries*, or the agent of the return step, which writes as this step
writes — and by the orchestrator of `implement-task` where its skill names this file.

The foundation step writes the entries the task carries: each row of *Settlements to record* whole,
in the place its column *Goes to* names — as an entry of its kind where the column names an entry —
one no code makes true included — its meaning the row's and its wording the writer's (WAY-134); each
projected entry of the task's sources that its code makes true or its plan item assigns, whole as
the readiness gate approved it, or the part the code makes true (WAY-126); and each entry a reviewed
spec or the plan names. Each entry is written by following the pinned `SKILL.md` of its element, on
the task branch, to reach the main branch with the code in the request, and none is left for later
(WAY-01). That file is `elements/decisions/skill/SKILL.md` for a decision,
`elements/invariants/skill/SKILL.md` for an invariant, `elements/glossary/skill/SKILL.md` for a
glossary term, `elements/part-map/skill/SKILL.md` for a part of the map and
`elements/environment-facts/skill/SKILL.md` for an environment fact, in the pinned the-way; a skill
that file or a file it reads names by its name alone — `record-invariant`, `update-part-map` or
another — is the `SKILL.md` whose frontmatter `name:` is that name, which a search of the files
named `SKILL.md` for that line finds, and the writer reads it as a file where it has no skill tool,
as the cycle's types have none (WAY-368). A row whose column names no element, a skill or
instruction file, a guidelines discipline or the product's data or code, is written in its place by
the rule of that place, in the same change as the code, and no entry is written for it. A row whose
settlement the writer's search of the whole foundation (WAY-33) finds already stated becomes no
second entry: the writer ties the row to that entry, and the request names both, as
`task-cycle/skill/request_template.md` gives (WAY-134). A plan member writes only the
projected entries its plan item assigns; one that falls to another item returns to the plan through
a blocked draft request. The writer keeps in its report, for each entry, one sentence of its meaning
in English and one in the task document's language, and marks the entry `row <n>`, `projected` or
`the cycle's` — the last for an entry no row and no projected entry carries whole, which the request
puts before the human (WAY-114). A question for the human arises only where the writer has no
recommendation, an entry would change the meaning of an approved decision beyond what the accepted
task document or plan carries (WAY-30), a row's meaning cannot hold — the code shows an exception
the row does not allow, or the row collides with a current entry other than as the task commands —
or a row's entry needs a value neither the row nor the work gives — save a decision's *Rejected*,
which takes the ways not chosen that the row's source keeps, `none considered` where the human
said so, or `unknown`, as the decisions' template gives (WAY-134); two decisions colliding with no
precedence recorded raise one too, unless what the human accepted gives the outcome and the change
may write the decision that prevails: then the writer records the precedence in that decision, marks
it `the cycle's`, and keeps in its report the passages of what the human accepted that give the
outcome, quoted (WAY-25). The writer never writes a row with another meaning: it returns such a
question with the status `blocked`, and the orchestrator opens the blocked draft request holding
it, as `task-cycle/skill/request_template.md` gives.
