# Decision entry template

This file defines how an entry in the decision log (`decisions.md`) is written. The log is
append-only: an entry is never edited after it is added. What is in force today is a separate
view, generated by a script from the log.

## Where entries go

- Every entry is appended at the end of `decisions.md`, in the order it is written. The log has
  no topical sections.
- An entry is either a **decision version** or a **review**.
- An existing entry is never edited. A correction, however small, is a new version.

## Decision version

```markdown
### WAY-NN/V — <the question this decision answers>

<1–3 binding sentences>

- **Change:** new decision | <kind> · previous: WAY-NN/V-1
- **Scope:** <parts from the part map>
- **Based on:** <facts about the environment> | none
- **Relations:** derives from WAY-x · narrows WAY-y · related to WAY-z | none
- **Outranks:** WAY-x, WAY-y | none
- **Verification:** level 1 | 2 | 3 — <…>
- **Review when:** <observable state> · check by: YYYY-MM-DD | none
- **Origin:** <where the full reasoning lives> | inherited — searched: <…>; found: <…> | none
- **Change approver:** area default | <who>
- **Approved by:** <who>, YYYY-MM-DD

*Rationale:* <…>
*Rejected:* <…> | none considered
*Consequences:* <…>
```

In version 2 and later, *Rationale* becomes *Rationale for change*.

### Every field, every entry

Every field is present in every version, in one of three states:

| State | Meaning | Format guard |
|---|---|---|
| a value | known | passes |
| `none` | the author states there is nothing here | passes |
| `TODO — <what is missing>` | known to be unknown | warning |
| field missing | forgotten | error |

`none` is a statement, not a blank. Write it only when you know there is nothing; when a
source is silent, write `TODO`.

### Fields and their readers

A field stays in the template only while someone or something reads it.

| Field | Who reads it, when |
|---|---|
| number (heading) | references from entries, tests and code; the view script |
| version (heading) | the view script — the latest version is in force. A reference to a specific version (`WAY-06/1`) is historical and never flagged |
| question (heading) | the author and the skill: is this a new version of an existing number, or a new number? The view uses it as the title |
| binding sentences | the agent checking a change against the decision; the content fingerprint |
| Change | the view script (history line, tombstone); reference flags, by kind |
| Scope | choosing which decisions to check for a task: changed files → parts → decisions |
| Based on | reviewing the decision when a fact changes |
| Relations | impact assessment; reference flags |
| Outranks | the agent resolving a collision between two decisions |
| Verification | level 1: the quality gate; level 2: the reviewing agent; level 3: a human |
| Review when | the view (pending checks); the agent working on a task in scope; the format guard (a passed date without a review) |
| Origin | whoever wants to change the decision and needs the full reasoning; the next agent, so it does not repeat a search |
| Change approver | the agent that needs a new version approved |
| Approved by | a human considering a change; the format guard — a version without it is an error |
| Rationale / Rationale for change | the agent in a borderline case; a human considering a change |
| Rejected | the agent, before proposing an option already rejected |
| Consequences | the closing step of a task: what the decision forces on further work |

## Binding sentences

- One to three sentences: the first paragraph under the heading.
- Present tense, describing a state that is to be true, concrete enough to check.
- Normative words — *must*, *must not* — appear only here, in lower case. *Should*, *will*,
  all-caps and exclamation marks do not appear.
- Say what is, rather than what is not, unless the forbidden thing is concrete and visible in
  a change.
- An exception foreseen in advance is written into the binding sentences ("X is allowed when
  Y"); acting on it is then not a contradiction.

The content fingerprint covers only the binding sentences, so a fix to the rationale does not
flag references.

## Decision or invariant

- An **invariant** is a sentence about the product that is true or false on every commit, with
  a method of checking it. It says nothing about why, or about what was rejected.
- A **decision** is a choice between options, with a rationale. It binds future choices,
  including ones that cannot be checked on a commit: direction, trade-off principles,
  non-goals.
- **Test:** can you point to a commit on which the sentence is false? Yes — it is an invariant.
  It is about a choice or a direction — it is a decision.
- Tests live only with invariants. A decision is verified through the invariants derived from
  it.

## Numbers and versions

- A number stands for a question. A new question gets a new number; a new answer to an existing
  question is a new version of that number.
- A new version carries the full binding sentences, all fields and *Consequences* — they
  describe the state. *Rationale for change* and *Rejected* describe only this change; the view
  reaches them through the history line.
- When a new decision answers a question that an older decision answered in passing, the
  sentence moves to the new decision, and the older one gets a new version without it.
- A new rule next to an existing decision answers a new question: it gets a new number and
  `related to` its neighbour.

## Kinds of change

The list is closed. Adding a kind takes a decision.

| Kind | What changes | Binding sentences vs previous version | References to the decision |
|---|---|---|---|
| new decision | — (version 1) | — | — |
| editorial correction | wording, not meaning | differ | not flagged, once a human confirms the meaning is unchanged |
| rationale change | the reasoning only | identical | not flagged |
| field change | fields only | identical | flagged only when *Based on* changes |
| new wording | what the decision says | differ | flagged |
| narrowing | an exception is added | differ | flagged softly |
| challenge | nothing yet — the decision is in doubt | identical | still in force; the view shows a warning |
| replacement | the whole answer | differ | flagged sharply; *Consequences* says what happens to what was built on the old version |
| repeal | the question no longer needs an answer | none | the view shows a tombstone — one line in place of the decision; flagged sharply |

A *narrowing* version writes the exception into the decision itself. The relation `narrows` is
used when a different, more specific decision deliberately goes against this one.

## Relations and precedence

- *Relations* use a closed list: `derives from` (a higher decision this one serves), `narrows`
  (this decision deliberately goes against the one named, in a narrower area), `related to`
  (anything else).
- Only the newer entry writes a relation; the view shows the reverse at the older entry.
- *Outranks* names decisions that give way to this one when both apply and collide. It holds
  only for the pairs listed; nothing is inferred along a chain. Two decisions that outrank each
  other are an error.
- When a new decision is less important than an existing one, the existing one gets a
  *field change* version that adds the new number to its *Outranks*.
- `narrows` says the other decision does not apply here; *Outranks* says both apply and this
  one wins a collision.
- A collision between two decisions with no precedence recorded stops the work: a human records
  the precedence as a new version of one of them.

## Verification

- Level 1 — invariants derived from the decision. Until invariants have their own template,
  name each one in working form.
- Level 2 — an agent compares a change with the decision, using a pair of examples:
  `complies:` and `violates:`.
- Level 3 — a human assessment, leaving a trace of who and when.
- Level 2 or 3 only while no invariant can be derived today. When one is derived, the decision
  moves to level 1 by a *field change*.

```markdown
- **Verification:** level 2 — an agent compares the change with the decision:
  - complies: <…>
  - violates: <…>
```

## Trade-off principles and non-goals

- A trade-off principle is an ordinary decision. Its question is "What do we choose when A
  conflicts with B?", its binding sentence "When A conflicts with B, we choose A.", and its
  *Rationale* names the problem the principle solves.
- Precedence between principles is recorded with *Outranks*, pair by pair. There is no single
  ranked list.
- A non-goal is an ordinary decision, one per non-goal: "The product does not do X", with the
  reason. Non-goals live only at product level; a task's exclusions live in its specification.
  A non-goal that can be checked on a commit gets a derived invariant.

## Review

A decision that rests on a prediction carries *Review when*: an observable state and a check-by
date. The field does not lift the decision; it tells the agent working in scope to check whether
the state has occurred. On the date, a review entry is appended:

```markdown
### WAY-NN · review YYYY-MM-DD

- **Result:** condition not met — <what was observed>
- **Next check:** YYYY-MM-DD
- **Checked by:** <who>
```

*Result* takes one of three forms:

- `condition not met — <what was observed>`; *Next check* is a date;
- `condition met, decision kept — <why>`; *Next check* is a date or `none`;
- `condition met — changed in WAY-NN/V+1`; *Next check* is `none`, and the new version sets its
  own *Review when*.

`Next check: none` closes the condition. A review is not a new version of the decision.

*Review when* is only for a state of the world or the product that someone is waiting for.
A change in another decision this one depends on is caught by reference flags, not by this
field.

## Origin

*Origin* points to where the full reasoning lives: a research document, a design document, a
merge request, a ticket, or a file at a fixed commit — never to anything deleted when its task
closes. When the whole reasoning is in the entry, it is `none`. Documents go in *Origin*;
*Based on* names facts about the world. The task a decision was made in is not recorded: git
history gives it.

## Inherited decisions

A decision recovered from the existing state of a product:

- *Origin* records what was searched and what was found: `inherited — searched: <…>; found:
  <…>`.
- *Rationale* is `unknown`, or quoted from the source *Origin* points to. A rationale proposed by
  an agent goes to a human as a question, never into the entry.
- While the rationale is unknown, any change to the decision is approved by a human.

## Approval

- Every version carries *Approved by*: who and when.
- Who approves changes is set per area by a process rule, not per entry. *Change approver*
  names someone only when the area default does not apply.

## What the format guard checks

- Headings: `### WAY-NN/V — <question>` or `### WAY-NN · review YYYY-MM-DD`; versions of a
  number are consecutive.
- Append-only: compared with the previous commit, the log only grows at the end.
- Every field is present; `TODO` gives a warning.
- Binding sentences: one to three; no *should*, *will* or all-caps.
- *Change*: `new decision` exactly in version 1; in later versions a kind from the list, with
  `previous:` pointing to the version before.
- Binding sentences are identical to the previous version for *rationale change*,
  *field change* and *challenge*, and absent for *repeal*.
- Every number in *Relations*, *Outranks* and `previous:` exists.
- *Outranks*: no two decisions outrank each other.
- *Review when*: a passed check-by date without a later review gives a warning;
  `condition not met` requires a date in *Next check*; `changed in WAY-NN/V+1` requires that
  version to exist.
- *Approved by* is present in every version.
- Every example in `decision-examples.md` matches its version in the log word for word.

## Examples

Examples live in `decision-examples.md`: verbatim copies of versions from the log. An example is
a copy of a version that was already approved, so adding one needs no new decision.
